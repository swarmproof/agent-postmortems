# RELEASING — cutting a versioned snapshot of the corpus

*How a GitHub release of the corpus is produced, as practised for `2026.10`, `2026.11`,
`2026.11.1` and `2026.11.2`, and what has to change in the repo alongside it.*

Releases are **snapshots of a publish commit**. The always-latest export lives on `main`
(`export/*.json`, regenerated by `.github/workflows/publish.yml`); a release pins one of
those export commits under a CalVer tag, so a paper or a downstream tool can cite a fixed
corpus. The assets are rebuilt by `scripts/build_release.py` from a clean checkout of that
commit, and the build fails unless the rebuilt exports equal the committed ones byte for
byte, so the assets are both reproducible and identical to `export/*.json` at the tag.

## 1. Pick the commit

Tag the **publish-workflow commit**, never a merge commit or a docs change. The publish
workflow (`publish.yml`) runs on every push to `main` that touches `incidents/`,
`schema/` or `scripts/`, and daily at 07:00 UTC. It regenerates `export/*.json`, backfills
`archive_url` snapshots, rewrites the README stats block, and commits the result as:

```
chore(export): refresh exports and source archives [skip ci]
```

Every release tag so far resolves to a commit with that subject. Confirm the latest one and
take its **full SHA**:

```bash
git fetch origin main
git log --oneline -5 origin/main           # the top commit should be the chore(export) one
SHA=$(git rev-parse origin/main)
git show -s --format=%s "$SHA"             # must print the chore(export) subject
gh run list --workflow publish.yml --limit 3   # the run for that push must be "success"
```

If the top of `main` is not a `chore(export)` commit, either wait for the publish run
that is in flight or trigger one (`gh workflow run publish.yml`) and re-check.

## 2. Choose the tag

CalVer, `YYYY.MM` for the first release in a month and `YYYY.MM.N` for each further
release in that month (`2026.10`, `2026.11`, `2026.11.1`, `2026.11.2`). The tag is the
version string used everywhere else (release title, `CITATION.cff`, Zenodo).

```bash
gh release list --limit 10                 # confirm the next free tag
```

## 3. Build the assets from that commit

Build in a clean, separate checkout of `$SHA` so nothing local leaks in:

```bash
rm -rf /tmp/release-src /tmp/release-assets
git worktree add --detach /tmp/release-src "$SHA"
cd /tmp/release-src
SOURCE_DATE_EPOCH=$(git log -1 --format=%ct) \
  uv run scripts/build_release.py --tag "$TAG" --out /tmp/release-assets
(cd /tmp/release-assets && sha256sum -c SHA256SUMS)
cd - && git worktree remove /tmp/release-src
```

`/tmp/release-assets` then holds:

| asset | content |
|---|---|
| `incidents.json`, `scenarios.json`, `seeds.json` | the export contract, rebuilt from `incidents/` at `$SHA` |
| `incident.schema.json` | `schema/incident.schema.json` at `$SHA` |
| `CITATION.cff` | `CITATION.cff` at `$SHA` |
| `manifest.json` | tag, full commit SHA, record/incident/hazard/scenario/seed counts, schema, taxonomy and export-schema versions, sha256 and size of every other asset |
| `SHA256SUMS` | `sha256sum -c` checksums of all of the above |

**Reproducibility.** The exports carry no wall-clock time: their `generated_at` /
`corpus_as_of` stamp is the newest incident `date`, so they are a pure function of the
corpus. The only time in `manifest.json` is `SOURCE_DATE_EPOCH` (the commit time of `$SHA`
when unset). Anyone can rerun the block above on the same tag, with Python ≥ 3.10 and `uv`,
and get byte-identical files; the published `2026.11.1` and `2026.11.2` assets equal a
rebuild of the exports at their tags.

**Drift.** The script exits non-zero if the rebuilt exports differ from `export/*.json`
committed at `$SHA`. On a publish commit they never do, so a failure means the wrong
commit was picked (step 1). Pull requests deliberately do not commit exports, so drift is
checked only here and after the publish workflow pushes, never on pull-request CI.

**`CITATION.cff`.** The asset is the file as committed at `$SHA`, which still names the
previous release until step 6 lands. Bump `version` and `date-released` in a PR before
cutting the release if the asset should cite its own tag.

## 4. Write the notes

The notes have a fixed shape; copy the previous release (`gh release view 2026.11.2`) and
replace the figures and the change list. The **This snapshot** figures are the three
README stat rows at the tagged commit (`gen_readme_stats.py` writes them in the same
publish commit), so they never need recomputing by hand:

```bash
git show "$SHA:README.md" | sed -n '/STATS:START/,/STATS:END/p'
```

Structure, top to bottom:

1. One line: *A versioned snapshot of the **agent-postmortems** corpus — a structured, public
   database of real AI-agent failures.*
2. **This snapshot** — three bullets: `N incidents (R realized · H demonstrated hazards /
   near-misses), YYYY–YYYY`; `C of 19 failure classes represented; K CVE-backed`; the
   schema/taxonomy conformance line.
3. **Since <previous tag>** — what changed: the number of new records with the
   realized/hazard split and a one-paragraph summary of what they cover; corrections to
   existing records; tooling or pipeline changes visible to consumers. The counts come from
   the tag diff:

   ```bash
   PREV=2026.11.2
   git diff --name-only --diff-filter=A "$PREV" "$SHA" -- 'incidents/2*.yaml' | wc -l
   git diff --name-only --diff-filter=A "$PREV" "$SHA" -- 'incidents/2*.yaml' \
     | while read f; do git show "$SHA:$f" | grep -m1 '^incident_type:'; done | sort | uniq -c
   ```
4. **Assets** — the three export files, with `scenarios.json` linked to stampede and `seeds.json`
   to costbomb, followed by the line *Export entries carry natural-language trigger
   \*shapes\*, never runnable exploit payloads.*
   Then one line naming `manifest.json` and `SHA256SUMS` and how to verify:
   `sha256sum -c SHA256SUMS`.
5. **Use the data** — site URL, the always-latest raw export URL, `SCHEMA.md` and
   `TAXONOMY.md` links.
6. The CC-BY-4.0 / `CITATION.cff` line.

## 5. Create the release

```bash
TAG=2026.11.3
M=/tmp/release-assets/manifest.json
N=$(python3 -c "import json,sys;print(json.load(open(sys.argv[1]))['counts']['records'])" "$M")
X=$(python3 -c "import json,sys;print(json.load(open(sys.argv[1]))['counts']['incidents'])" "$M")
Y=$(python3 -c "import json,sys;print(json.load(open(sys.argv[1]))['counts']['hazards'])" "$M")
gh release create "$TAG" \
  --target "$SHA" \
  --title "agent-postmortems corpus — $TAG ($N records: $X incidents, $Y hazards)" \
  --notes-file /tmp/release-notes.md \
  /tmp/release-assets/*
```

`--target` with the full SHA makes GitHub create the tag at that exact commit. Verify:

```bash
gh release view "$TAG" --json tagName,targetCommitish,assets
git fetch --tags origin && git rev-list -n1 "$TAG"      # equals $SHA
rm -rf /tmp/release-check && gh release download "$TAG" -D /tmp/release-check
(cd /tmp/release-check && sha256sum -c SHA256SUMS)       # uploaded bytes match the build
```

The title convention is `agent-postmortems corpus — <tag> (<N> incidents)`; `2026.11.2`
was published with the bare tag as its title and can be corrected with
`gh release edit 2026.11.2 --title "agent-postmortems corpus — 2026.11.2 (180 incidents)"`.

## 6. Update CITATION.cff in the same change

`CITATION.cff` carries the released version so that GitHub's "Cite this repository" box and
`cffconvert` emit the snapshot a reader can actually fetch. After the release exists, open a
PR to `main` that sets, from `gh release view "$TAG" --json tagName,publishedAt,url`:

```yaml
version: "2026.11.3"                 # the tag
date-released: "YYYY-MM-DD"          # the date part of publishedAt
repository-artifact: "https://github.com/swarmproof/agent-postmortems/releases/tag/2026.11.3"
```

and validate it before pushing:

```bash
uvx cffconvert --validate -i CITATION.cff
```

## 7. DOI via Zenodo (one-time setup, not yet done)

No DOI exists for this corpus yet, which is why `CITATION.cff` has no `doi` or
`identifiers` entry. Minting one is a Zenodo–GitHub integration that only the **repository
owner's Zenodo account** can enable; it is not something a contributor or a workflow can do:

1. Sign in at https://zenodo.org with the GitHub account that owns `swarmproof`, open
   **GitHub** under the account menu, and flip the switch for `swarmproof/agent-postmortems`.
2. From then on, **each GitHub release** triggers Zenodo to archive the release tarball and
   mint a version DOI, plus a concept DOI that always resolves to the latest version. Zenodo
   reads `CITATION.cff` for title, authors and license. The first DOI appears only for the
   first release published *after* the switch is on; earlier releases are not back-filled.
3. Add the DOIs to `CITATION.cff` and validate:

   ```yaml
   doi: 10.5281/zenodo.XXXXXXX          # the version DOI of the cited release
   identifiers:
     - type: doi
       value: 10.5281/zenodo.YYYYYYY    # the concept DOI (all versions)
       description: "Concept DOI; resolves to the latest release"
   ```

   The version DOI changes with every release, so step 6 then also updates `doi`.

Until step 1 is done, cite by tag and release URL as `CITATION.cff` currently does.

- [ ] Notes follow the structure above; **This snapshot** figures equal the README stats block at `$SHA`
